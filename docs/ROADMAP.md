# План развития мультилендинга

## 1. Цель клиента

Клиенту нужен мультилендинг для сбора низкочастотного поискового трафика. Практически это означает систему, которая может создавать много посадочных страниц под конкретные запросы:

```text
услуга + тип техники + бренд + модель + география
```

Примеры:

```text
ТО Yamaha R6 в Москве
ремонт квадроцикла BRP Outlander в Москве
диагностика Polaris Sportsman в Москве
покраска бака Harley-Davidson в Москве
```

Ориентир клиента в 10 000 страниц нужно воспринимать как потенциальный масштаб системы, а не как задачу вручную сделать 10 000 HTML-файлов.

## 2. Принципиальный подход

Правильная модель: данные + шаблон + правила качества + генерация URL.

Пользователь видит обычную посадочную страницу услуги. Генератор, статусы индексации, sitemap и SEO-поля остаются невидимыми.

Не нужно делать страницы, которые отличаются только названием бренда. Это слабая SEO-стратегия и риск санкций за низкокачественный автогенерированный контент.

## 3. Что должен содержать production-мультилендинг

### 3.1. Данные

Нужно расширить текущий `data/landings.json` до нормальной модели данных:

- услуги;
- типы техники;
- бренды;
- модели;
- подуслуги;
- симптомы;
- цены;
- FAQ;
- примеры работ;
- изображения;
- связанные страницы;
- статус индексации;
- canonical/redirect-правила.

Минимальные сущности:

```text
services
vehicle_types
brands
models
locations
landing_pages
faqs
works
prices
```

### 3.2. Матрица страниц

Нужна таблица допустимых комбинаций. Не все комбинации стоит публиковать.

Пример статусов:

```text
draft
index
noindex
canonical_to_parent
redirect
archived
```

Правило: в sitemap попадают только страницы со статусом `index`.

### 3.3. Качество контента

Для каждой посадочной нужно минимум:

- уникальный H1;
- уникальный title;
- уникальный description;
- конкретный lead;
- 4-8 работ по теме;
- 2-5 FAQ;
- блок брендов/моделей;
- связанные услуги;
- CTA;
- контакты;
- canonical;
- корректный robots meta.

Для важных страниц желательно добавить:

- частые неисправности конкретной модели;
- особенности обслуживания;
- расходники;
- реальные кейсы;
- фото работ;
- диапазоны цен;
- сроки.

## 4. Рекомендуемые этапы разработки

### Этап 1. Довести MVP до демонстрационного состояния

Статус: базово сделано.

Что уже можно показать:

- страницы генерируются из `data/landings.json`;
- есть разные URL под услуги, бренды и модели;
- пользовательский интерфейс не показывает служебные SEO-статусы;
- `sitemap.xml` включает только страницы со статусом `index`;
- страница со статусом `noindex` открывается, но не попадает в sitemap;
- шаблон содержит коммерческие блоки из структуры исходного сайта: услуги, бренды, запчасти, покраска, ателье, контакты.

Что можно улучшить перед production:

- добавить 20-50 посадочных страниц вместо 6;
- расширить JSON-данные по брендам и моделям;
- добавить больше FAQ;
- добавить страницу списка всех направлений только для внутренней проверки;
- удалить временные PNG-скриншоты из репозитория перед передачей, если они не нужны.

Результат этапа: заказчик видит рабочий прототип и понимает, как из данных появляются страницы.

### Этап 2. Собрать семантическую матрицу

Нужно собрать запросы по направлениям:

- ремонт мотоциклов;
- диагностика;
- ТО;
- двигатель;
- подвеска;
- тормоза;
- электрика;
- карбюраторы;
- шиномонтаж;
- квадроциклы;
- снегоходы;
- лодочные моторы;
- покраска;
- запчасти;
- эвакуатор;
- хранение;
- ателье.

Затем разложить по брендам:

```text
Honda, Yamaha, Kawasaki, Suzuki, Harley-Davidson, BMW, Ducati, KTM,
Triumph, BRP, Arctic Cat, Polaris, Johnson, Evinrude, Tohatsu
```

И по моделям, где есть спрос.

Результат этапа: таблица страниц-кандидатов с приоритетом и статусом.

### Этап 3. Ввести правила публикации

Перед публикацией страница должна пройти чек:

- запрос существует;
- услуга реально оказывается;
- есть уникальный текст;
- есть хотя бы 4 релевантные работы;
- есть FAQ;
- есть связанные страницы;
- нет дубля другой страницы;
- выбран статус `index` или `noindex`;
- корректный canonical.

Страницы с недостаточным контентом должны оставаться `noindex` или `draft`.

### Этап 4. Перенести в production-стек

Владелец сообщил, что текущий сайт реализован на Webasyst Shop-Script. Поэтому production-внедрение лучше делать одним из двух способов:

1. Плагин Webasyst.
2. Модуль/расширение темы Webasyst.

Рекомендация: для 10 000 страниц лучше плагин, потому что это уже бизнес-логика, а не только внешний вид.

Плагин должен уметь:

- хранить матрицу страниц;
- импортировать CSV/XLSX;
- генерировать URL;
- отдавать страницу через один шаблон;
- управлять `index/noindex`;
- генерировать sitemap;
- задавать canonical;
- показывать список страниц в админке;
- массово включать/выключать страницы.

### Этап 5. Аналитика и обратная связь

Нужно подключить:

- Яндекс.Метрику;
- Google Search Console, если актуально;
- Яндекс.Вебмастер;
- события формы;
- клики по телефону;
- клики WhatsApp/Telegram;
- UTM/landing URL в заявке.

В CRM или письме заявка должна содержать:

```text
URL страницы
H1 страницы
услуга
бренд
модель
тип техники
источник перехода
```

Иначе невозможно понять, какие посадочные страницы приносят лиды.

### Этап 6. Масштабирование

Масштабировать нужно партиями:

1. 50 страниц.
2. 200 страниц.
3. 500 страниц.
4. 1 000+ страниц.
5. 10 000 только после проверки индексации и качества.

После каждой партии:

- проверить индексацию;
- посмотреть показы/клики;
- найти дубли;
- улучшить слабые страницы;
- закрыть мусорные страницы в `noindex`;
- усилить страницы, которые получают показы.

## 5. Что не стоит делать

- Не публиковать сразу 10 000 страниц без контроля качества.
- Не делать страницы только с заменой бренда в H1.
- Не показывать пользователю служебные статусы вроде `index/noindex`.
- Не включать в sitemap страницы со слабым контентом.
- Не делать бесконечные комбинации без реального спроса.
- Не смешивать пользовательский лендинг и админскую таблицу генератора.

## 6. Ближайший практический план

1. Подтвердить с заказчиком структуру направлений из текущего сайта.
2. Собрать список услуг и подуслуг.
3. Собрать список брендов и моделей.
4. Подготовить CSV с первыми 50-100 страницами.
5. Расширить генератор под импорт CSV или нормализованный JSON.
6. Добавить внутреннюю страницу предпросмотра матрицы.
7. Добавить больше уникальных блоков для модели/бренда.
8. Подготовить Webasyst-план внедрения.
9. Согласовать, будет ли это плагин или доработка темы.
10. После согласования переносить прототип в production.

## 7. Критерии готовности production-версии

Production можно считать готовым, когда:

- страницы создаются из данных, а не вручную;
- есть управление статусами;
- sitemap генерируется автоматически;
- формы передают URL и тематику страницы;
- нет технических данных в пользовательском интерфейсе;
- есть аналитика конверсий;
- есть контроль дублей;
- есть процесс добавления новых страниц;
- есть понятная инструкция для контент-менеджера.

## 8. Как использовать текущий MVP

Текущий MVP нужен для демонстрации:

- как выглядит посадочная;
- как меняется контент под услугу/бренд/модель;
- как работает генерация URL;
- как `noindex` остается техническим параметром;
- как sitemap включает только индексируемые страницы.

Это не финальная production-система, а прототип для согласования подхода и следующей разработки.

## 9. Что показать заказчику

При передаче репозитория имеет смысл показать не только главную страницу, а несколько разных URL:

```text
/index.html
/landings/to-yamaha-r6-moskva/
/landings/remont-kvadrociklov-brp-outlander-moskva/
/landings/pokraska-baka-harley-davidson-moskva/
/sitemap.xml
```

На что обратить внимание заказчика:

- это не ручные страницы, а результат генерации из данных;
- видимая страница выглядит как обычный лендинг сервиса;
- структура позволяет масштабировать страницы партиями;
- для production на Webasyst потребуется отдельная реализация в виде плагина или доработки темы;
- 10 000 страниц нельзя публиковать сразу без семантической матрицы и контроля качества.
